## 0. rev.2에서 무엇이 바뀌었나

시안 개편의 본질은 **"살림 블로그 → 라이프스타일 매거진"으로의 스코프 확장**이다.
디자인 변경이 아니라 **서비스 정의 자체가 바뀐 것**이므로, 데이터 모델까지 영향이 간다.

| 축 | rev.1 | rev.2 |
|---|---|---|
| 브랜드명 | 살림의 기준 | **둘의 기준** (태그라인 `OUR EVERYDAY STANDARD` 유지) |
| 정체성 | 신혼부부 살림 리뷰 **블로그** | 직접 경험한 라이프스타일 리뷰 **매거진** |
| H1 | 직접 써본 것만, 솔직하게 기록합니다 | **직접 써보고, 직접 가보고, 우리의 선택을 기록합니다** |
| 대상 | 물건 (가전·가구·주방·생활) | 물건 **+ 공간/경험 (여행·숙소·맛집) + 비교 콘텐츠** |
| 카테고리 | 가전·가구·주방·생활·여행·맛집 | 가전·가구·**생활용품**·여행·맛집·**비교 콘텐츠** (주방 삭제) |
| 섹션 | 6개 | 7개 (**여행 섹션 신설**) |
| 최근 섹션 | "우리 집 상황에 맞춰 찾아보세요" | **"최근 리뷰"** (Latest field notes) |
| 원칙 | 4개 | **5개** ("광고보다 경험 우선" 추가) |
| 테마 | 라이트 전용 | **라이트 + 다크 토글** |
| 푸터 | 블로그 소개 | **매거진 소개** |
| JSON-LD | WebSite, Organization | **+ Review(Product/Rating), Article** |

> **가장 중요한 함의**: "직접 써보고"와 "직접 가보고"는 **데이터 성격이 다르다.**
> 물건은 `구매가·사용기간·재구매의사`, 경험은 `총경비·박수·재방문의사`다.
> rev.1의 단일 `Review` 모델로는 담을 수 없어, 기술 명세서에서 **다형 리뷰 타입**으로 재설계했다.

## 1. 서비스 정의

### 1.1 한 줄 정의
> 부부가 **직접 사고, 직접 예약하고, 직접 다녀온** 것들의 장단점을,
> 시간이 지난 뒤 다시 평가해 기록하는 라이프스타일 리뷰 매거진.

### 1.2 다른 리뷰 매체와의 차별점 (= 제품 요구사항의 근거)

| 차별점 | 이를 구현하는 기능 |
|---|---|
| 협찬이 아닌 **직접 경험** | `acquisitionType` (구매/예약/방문) + "직접 구매·직접 예약·직접 다녀옴" 배지 |
| 개봉기가 아닌 **누적 경험** | `experienceScale` (N개월 사용 / N박 숙박 / N인 식사) |
| 점수가 **시간에 따라 변한다** | `ReviewScore` 이력 → "처음 4.2 → 현재 4.5" + "평가 변경" 배지 |
| 장점보다 **단점을 먼저** 보여준다 | `ProsCons` 를 목록 카드 단계에서 노출 |
| 제품이 아니라 **우리 상황**으로 찾는다 | 상황 태그 필터 |
| **다시 할 의향**이 최종 결론 | `wouldRepeat` (재구매 / 재방문 / 재숙박) |
| **[rev.2]** 하나가 아니라 **나란히 놓고 비교** | `COMPARISON` 리뷰 타입 (예: 조잔케이 vs 노보리베츠) |

이 7가지가 데이터 모델의 뼈대이며, 일반 블로그 CMS를 쓰지 않고 **자체 어드민**을 만드는 이유다.

> rev.1의 `purchaseType` / `usageMonths` / `buyAgain`을 각각
> `acquisitionType` / `experienceScale` / `wouldRepeat`로 **일반화**했다.
> 물건과 경험을 같은 축으로 다루기 위한 최소 추상화다.

### 1.3 타깃

| 구분 | 설명 | 주요 진입 경로 |
|---|---|---|
| 1차 | 혼수/신혼집 준비 중인 예비·신혼부부 | 검색 (`식기세척기 2인 가구`) |
| 2차 | **둘이 여행 계획 중인 커플** *(rev.2 신규)* | 검색 (`삿포로 3박4일 경비`, `그랑벨 호텔 후기`) |
| 3차 | 자취 → 동거 전환, 첫 독립 가구 | 검색, SNS 공유 |
| 4차 | 재구매·교체 시점의 기존 가구 | 검색, 뉴스레터 |

**핵심 진입은 검색(롱테일 키워드)** → SEO가 최우선 비기능 요구사항.
여행 확장은 SEO 관점에서 **검색량이 큰 키워드 풀을 새로 얻는다**는 의미가 있다.
다만 여행·숙소 리뷰는 경쟁(네이버 블로그·트립어드바이저)이 훨씬 치열하므로,
**"총경비 실공개 + 실제 동선"** 같은 차별 축이 없으면 유입이 어렵다. (§8 이슈 #7)

#### 🔴 발견된 정합성 문제 3건

시안 rev.2를 전수 검사한 결과, 아래 3건은 **구현 전에 반드시 정리**해야 한다.

**① 삭제된 '주방'이 카드에 살아있다**

카테고리 그리드에서는 '주방'이 사라졌지만, 최근 리뷰 그리드에는 여전히
`data-category="주방"` 카드(프라이팬 리뷰)가 `<span class="tag">주방</span>`을 달고 존재한다.
→ **선택 필요**: (a) '주방'을 `living`(생활용품)에 흡수, (b) 카테고리로 복원.
→ **권장 (a)**. "생활용품 = 실제로 사용한 생활의 도구"가 주방도구를 충분히 포괄한다.
   기존 URL이 있다면 `/categories/kitchen` → `/categories/living` **301 리다이렉트**.

**② 네비게이션이 카테고리와 불일치**

| | 항목 |
|---|---|
| 카테고리 그리드 (6) | 가전 · 가구 · 생활용품 · 여행 · 맛집 · 비교 콘텐츠 |
| 헤더 네비 (5) | **생활** · 가전 · 가구 · 여행 · 맛집 |
| 푸터 (4) | 가전 · 가구 · 여행 · 맛집 |

네비는 '생활'(구 이름), 카테고리는 '생활용품'. 네비에 '비교 콘텐츠'가 없다.
→ **네비 = 카테고리 6종과 이름·순서 동일하게 정렬.** 단일 소스(`GET /categories`)에서 렌더링해
   수동 불일치가 원천적으로 불가능하게 만든다.

**③ 카드의 `data-category`가 카테고리 체계 밖이다**

카드에 실제로 쓰인 값: `가전 · 가구 · 생활 · 주방 · 맛집 · 여행 · 숙소 · 여행지`
→ **`숙소`, `여행지`는 카테고리가 아니라 여행의 하위 타입**이다.
→ 카테고리는 `travel` 하나로 두고, `reviewType`(`TRIP` / `STAY` / `PLACE`)으로 분기한다.
   화면 표시 라벨(`여행 일정` / `숙소 리뷰` / `여행지 비교`)은 타입에서 파생시킨다.

**상황 태그 (다중 선택, 시안의 필터 칩 순서 유지)**

| sortOrder | slug | 이름 | 자동 부여 규칙 |
|---|---|---|---|
| 1 | `two-person` | 2인 가구 | 수동 |
| 2 | `small-home` | 좁은 신혼집 | 수동 |
| 3 | `dual-income` | 맞벌이 부부 | 수동 |
| 4 | `cooks-often` | 요리를 자주 하는 집 | 수동 |
| 5 | `less-cleaning` | 청소 시간을 줄이고 싶은 집 | 수동 |
| 6 | `value-for-money` | 가성비 우선 | 수동 |
| 7 | `long-lasting` | 오래 쓰는 제품 | `experienceUnit=MONTH AND experienceScale >= 12` 시 어드민에서 **추천** |

#### 🔴 rev.2 필터 불일치 — 최우선 수정 대상

**필터 칩은 8개 그대로인데, 카드에는 여행·숙소·맛집이 새로 들어왔다.**
새 카드들의 태그는 기존 칩 어디에도 매칭되지 않는다.

| 카드 | `data-tags` | 매칭되는 칩 |
|---|---|---|
| 그랑벨 호텔 | `직접 예약, 3박 숙박, 재숙박 의사 있음` | **없음** |
| 삿포로 3박4일 | `2인 가구, 직접 다녀옴, 3박4일, 재방문 의사 있음` | `2인 가구` 만 |
| 성수 맛집 | `2인 가구, 직접 방문, 2인 식사, 재방문 의사 있음` | `2인 가구` 만 |

즉 **"맞벌이 부부"나 "가성비 우선"을 누르는 순간 여행·숙소·맛집 카드가 전부 사라진다.**
"최근 리뷰"라는 섹션 제목과 정면으로 충돌한다.

또한 같은 개념이 3가지 표현으로 쪼개져 있다:
`재구매 의사 있음` / `재방문 의사 있음` / `재숙박 의사 있음`

**해결안 — 태그를 2계층으로 분리한다**

| 계층 | 성격 | 예시 | UI |
|---|---|---|---|
| **A. 경험 방식** (자동) | 어떻게 얻었나 | 직접 구매 · 직접 예약 · 직접 다녀옴 · 직접 방문 | 카드 배지 (필터 아님) |
| **B. 상황** (수동) | 누구에게 맞나 | 2인 가구 · 맞벌이 부부 · 가성비 우선 · 좁은 신혼집 | **필터 칩** |
| **C. 규모** (자동) | 얼마나 | 6개월 사용 · 3박 숙박 · 2인 식사 | 카드 배지 (필터 아님) |

- A·C는 `acquisitionType` / `experienceScale`에서 **자동 생성**한다. 수동 태그로 두지 않는다.
- **필터 칩은 B만 노출**한다.
- `재구매/재방문/재숙박 의사 있음` → **`wouldRepeat` 불리언 하나**로 통합하고,
  카드 배지 문구만 타입별로 다르게 렌더링한다. 칩 라벨은 **"다시 할 의향 있음"**으로 중립화.
- 여행·맛집 카드도 B 태그(`2인 가구`, `가성비 우선` 등)를 **반드시 1개 이상** 부여해
  어떤 칩을 눌러도 결과가 고르게 나오도록 한다.

**추가 권장 상황 태그** (여행 확장 대응)

`주말 여행` · `해외 여행` · `기념일` · `첫 방문` — 필터 칩이 8개에서 12개가 되면 모바일에서 2줄이 되므로, 칩 영역을 가로 스크롤(`overflow-x: auto` + 스크롤 스냅)로 처리한다.

> `다시 할 의향 있음`은 `wouldRepeat=true` 에서 **자동 파생**시켜 수동 태깅 실수를 막는다.
> 마찬가지로 `오래 쓰는 제품`은 `experienceScale >= 12개월` 자동 부여 후보. 단 MVP에서는 수동 유지 + 어드민 추천만 표시.

## 3. 페이지별 상세 기획

### 3.1 홈 `/`

시안의 섹션 순서를 **그대로 유지**한다. 각 섹션의 데이터 출처를 명시한다.

| # | 섹션 | 데이터 출처 | 갱신 |
|---|---|---|---|
| 0 | 헤더 (sticky) + **테마 토글** | 카테고리 목록 | 정적 |
| 1 | 히어로 — *직접 써보고, 직접 가보고* | 정적 카피 + 히어로 이미지(어드민 설정) | 정적 |
| 2 | 트러스트 스트립 (4지표) | `GET /stats/summary` 집계 | 1시간 캐시 |
| 3 | 카테고리 그리드 (6) — *무엇을 선택하기 전에 경험부터* | `GET /categories` (+ publishedCount) | ISR |

**§2 트러스트 스트립 지표 정의 (중요)**

| 라벨 | 계산식 |
|---|---|
| 직접 사용 리뷰 | `COUNT(review WHERE status=PUBLISHED)` |
| 3개월 이상 사용 | `COUNT(review WHERE type=PRODUCT AND experienceScale >= 3)` |
| 직접 구매 비율 | `COUNT(acquisitionType IN (PURCHASE, BOOKING, VISIT)) / COUNT(*) × 100` |
| 최종 업데이트 | `MAX(publishedAt, updatedAt)` → `YYYY.MM` |

> 이 수치는 신뢰의 근거이므로 **하드코딩 금지**. 반드시 실제 집계값을 노출한다.

> ⚠️ **rev.2 라벨 재검토 필요.** 시안은 여전히 "직접 사용 리뷰 / 3개월 이상 사용 / 직접 구매 비율"이라
> **물건 기준 문구**를 쓰고 있다. 여행·숙소가 절반을 차지하면 "3개월 이상 사용"은 의미가 없어진다.
> → 제안: `직접 경험한 리뷰` / `장기 사용·재방문 기록` / `직접 비용 지불 비율` / `최종 업데이트`

**§8 원칙 5개 (rev.2에서 1개 추가)**

1. 직접 사용한 것만 · 2. 단점을 숨기지 않기 · 3. 가격과 기간 함께 기록 ·
4. 시간이 지나면 업데이트 · 5. **광고보다 경험 우선** — *후원 여부가 아니라 실제로 살아본 시간을 기준으로 기록합니다.*

> 5번은 rev.2의 매거진 전환과 직결된다. 여행·숙소는 협찬 제안이 들어오기 쉬운 영역이라,
> `acquisitionType`에 `SPONSORED` / `INVITED`를 명시적으로 두고 **배지로 구분 노출**하는 것이 이 원칙의 구현이다.

**§6 여행 섹션 명세 *(rev.2 신설)***

| 항목 | 내용 |
|---|---|
| 제목 | 둘이 다녀온 여행 / eyebrow `Travel, as we lived it` |
| 리드 | "직접 예약하고, 직접 다녀온 숙소와 여행지의 **동선·총경비·다시 갈 의향**을 기록합니다." |
| 레이아웃 | 3열 비대칭 `1.15fr .85fr .85fr` → 모바일 1열 |
| 카드 | 풀블리드 이미지 + 어두운 그라디언트 + 흰 텍스트 (물건 카드와 시각적으로 완전히 구분) |
| 카드 구성 | 유리 태그 · 제목(24px) · 한 줄 설명 · 별점 |

**카드 3종과 대응 타입**

| 표시 라벨 | `reviewType` | 예시 | 핵심 필드 |
|---|---|---|---|
| 여행 일정 | `TRIP` | 삿포로 3박 4일 | 총경비, 박수, 동선, 재방문 의향 |
| 숙소 리뷰 | `STAY` | 그랑벨 호텔 | 1박 요금, 숙박일수, 위치, 재숙박 의향 |
| 여행지 비교 | `COMPARISON` | 조잔케이 vs 노보리베츠 | 비교 대상 N개, 항목별 비교 |

> 리드 문구가 **"동선·총경비·다시 갈 의향"**을 약속하고 있다.
> 이건 카피가 아니라 **데이터 계약**이다. 세 필드는 필수 입력이고, 카드/상세에서 반드시 노출되어야 한다.
> 특히 **총경비 공개**가 이 섹션의 유일한 차별점이므로, 미입력 시 발행 불가로 강제한다.

**§7 필터 동작 명세 (시안 JS 재현 + 개선)**

- 시안: 클라이언트에서 `data-tags` 문자열 `includes()` 매칭 → **부분 문자열 오매칭 위험** (`2인 가구`가 `12인 가구`에 매칭될 수 있음)
- 개선: 태그를 배열로 다루고 `slug` 정확 일치로 판정
- 홈에서는 초기 6건만 클라이언트 필터. 필터 선택 시 **7건 이상이면 `/tags/[slug]`로 이동 유도** (더보기 링크)
- `aria-live` 상태 문구 유지: `"{태그} 조건에 맞는 리뷰 N개"`
- 결과 0건: 시안의 `.no-results` 문구 유지

**검색 동작 명세**

- 시안: 헤더 아이콘 → 모달 → 현재 페이지 내 카드 실시간 필터 (홈 한정)
- MVP: 모달에서 **디바운스 250ms 서버 검색** → 상위 5건 즉시 미리보기 + `Enter` 시 `/search?q=` 이동
- `⌘K` / `Ctrl+K` 단축키 추가 (시안에 없음, 저비용 고효용)

### 3.2 리뷰 상세 `/reviews/[slug]` — **신규 설계**

시안에 없는 페이지. 홈의 디자인 언어를 그대로 계승해 설계한다.

```
┌─ 브레드크럼: 홈 / 가전 / 삼성 12인용 식기세척기
│
├─ [헤더 영역]
│   eyebrow: 카테고리명
│   H1: 제목
│   메타: [직접 구매] [6개월 사용] [평가 변경?]  · 2026.08.01 업데이트
│   별점 4.3 / 5   (초기 점수와 다르면 "처음 4.0 → 현재 4.3" 병기)
│
├─ [커버 이미지]  4/3, next/image priority
│
├─ ★ [한눈에 보는 결론 박스]  ← 이 페이지의 핵심. surface-soft, radius-lg
│   ├ 한 줄 결론 (conclusion)
│   ├ 장점 N개 / 단점 N개  (success / warning 컬러)
│   ├ 구매 정보: 구매 시점 · 구매가 · 구매처 · 사용 기간
│   └ 재구매 의사: ✓ 있음 / ✗ 없음  (success / warning)
│
├─ [제휴 고지 배너]  ← 제휴 링크가 있는 글에만. 본문 시작 전 필수 노출
│
├─ [본문]  MDX 렌더링
│   └ 목차(ToC) — 데스크톱 우측 sticky, 모바일은 접이식
│
├─ [사용 기간별 재평가 타임라인]  ← ScoreHistory 2건 이상일 때만
│   개봉 직후 4.0 → 3개월 4.2 → 6개월 4.3   (각 시점 코멘트)
│
├─ [구매 링크 카드]  제휴 링크 (rel="sponsored nofollow noopener", /go/[id] 경유)
│
├─ [작성자 / 리뷰 원칙 요약 배너]
│
├─ [관련 리뷰 3건]  같은 카테고리 → 부족하면 공통 태그 순
│
└─ [댓글]
```

**필수 준수 사항**
- 제휴 링크 존재 시 **본문 상단**에 고지 문구 노출 (공정거래위원회 「추천·보증 등에 관한 표시·광고 심사지침」 준수). 푸터 고지만으로는 부족.
- 문구 예: `이 글에는 제휴 링크가 포함되어 있으며, 구매 시 일정액의 수수료를 받습니다. 구매 가격에는 영향을 주지 않습니다.`
- 협찬 리뷰(`acquisitionType = SPONSORED | INVITED`)는 **배지 색을 terracotta로 구분**하고 상단에 명시.

### 3.2.1 여행·숙소 상세의 결론 박스 변형 **[rev.2]**

같은 레이아웃을 쓰되, **결론 박스의 내용만 타입별로 교체**한다. 페이지 구조를 나누지 않는다.

| 타입 | 결론 박스 항목 |
|---|---|
| `PRODUCT` | 구매 시점 · 구매가 · 구매처 · 사용 기간 · **재구매 의사** |
| `TRIP` | 여행 시기 · 기간(N박) · **총경비(2인 기준)** · 주요 동선 · **재방문 의사** |
| `STAY` | 숙박 시기 · 숙박일수 · **1박 요금** · 위치/접근성 · **재숙박 의사** |
| `PLACE` | 방문 시기 · 방문 인원 · 1인당 지출 · 대기 여부 · **재방문 의사** |
| `COMPARISON` | 비교 대상 N개 · 항목별 비교표 · **"우리는 이걸 골랐다"** 결론 |

**여행 전용 추가 블록**
- `TRIP`: 일자별 동선 타임라인, 경비 내역 breakdown(항공/숙소/식비/교통/기타)
- `STAY`: 체크인·아웃 시각, 역/공항까지 도보·이동 시간
- `COMPARISON`: 비교표(모바일에서는 가로 스크롤 또는 카드 스택으로 전환)

> 총경비 breakdown은 **이 매거진이 네이버 블로그보다 나은 유일한 지점**이 될 수 있다.
> 구조화된 데이터로 저장하면 나중에 "3박4일 삿포로 평균 경비" 같은 집계 콘텐츠로 재활용 가능하다.

### 3.3 목록 페이지 `/reviews`, `/categories/[slug]`, `/tags/[slug]`

공통 컴포넌트 `ReviewListPage` 하나로 처리.

- 상단: `SectionHeading` (카테고리/태그명 + 설명)
- 필터 바: 카테고리 셀렉트 + 상황 태그 칩(다중) + 정렬(최신순 / 별점순 / 사용기간순 / 조회순)
- 그리드: 3열 → 1열, 12건 단위 페이지네이션 (SEO 위해 무한스크롤 대신 **페이지네이션 + `rel=next/prev`**)
- 필터 상태는 **URL searchParams에 반영** → 공유·뒤로가기·SEO 대응
  예: `/reviews?category=appliance&tags=2인가구,맞벌이부부&sort=rating&page=2`
- 정규화: 태그 조합 페이지는 `canonical`을 대표 URL로, 2페이지 이상은 `noindex` 검토

### 3.4 `/longevity`
홈 섹션의 전체 버전. 재평가 이력이 2건 이상인 리뷰만. 점수 상승폭 순 정렬 기본.

### 3.5 `/about`
리뷰 원칙 4개(시안 문구 유지) + 부부 소개 + 리뷰 프로세스 + 제휴 정책 + 문의 메일.
→ **E-E-A-T(경험·전문성·권위·신뢰) 신호로 SEO에 직접 기여**하므로 반드시 실제 내용으로 채운다.

### 3.6 어드민 `/admin`
- 별도 레이아웃 (사이트 헤더/푸터 미사용), `robots: noindex, nofollow`
- 리뷰 에디터 필드 구성:
  - 기본: 제목 / slug(자동생성+수정) / 카테고리 / 상황 태그(다중) / 상태
  - 신뢰 정보: 구매 유형 / 구매일 / 구매가 / 구매처 / 사용 개월 / 재구매 의사
  - 요약: 한 줄 결론 / 장점(순서형 리스트) / 단점(순서형 리스트) / 별점
  - 본문: MDX 에디터 (프리뷰 분할)
  - 미디어: 커버 이미지 / 본문 이미지 (드래그앤드롭 업로드)
  - 제휴: 링크 목록 (판매처 / URL / 가격)
  - SEO: 메타 제목 / 메타 설명 / OG 이미지
- **자동 저장(30초)** 및 발행 전 프리뷰(`/reviews/[slug]?preview=token`)
- 발행 시 Next.js on-demand revalidate 웹훅 호출

## 4. 주요 사용자 플로우

### 4.1 검색 유입 → 구매 결정 (핵심 퍼널)
```
구글/네이버 검색
  → /reviews/[slug] 진입
  → 결론 박스에서 3초 안에 판단 (한 줄 결론 + 단점 + 재구매 의사)
  → 본문 스크롤 or 제휴 링크 클릭 → /go/[id] → 판매처
  → 이탈 전 뉴스레터 or 관련 리뷰
```
**설계 함의**: 상세 페이지는 결론 박스가 스크롤 없이(above the fold) 보이도록 커버 이미지 높이를 제한한다(모바일 max 60vh).

### 4.2 상황 기반 탐색
```
홈 → "최근 리뷰" 섹션 → 상황 칩 선택
  → 6건 중 필터 → 부족하면 /tags/[slug] 전체 보기
  → 상세
```

### 4.2b 여행 계획 퍼널 **[rev.2 신설]**
```
검색 "삿포로 3박4일 경비"
  → /reviews/[trip-slug] 진입
  → 결론 박스에서 총경비 즉시 확인 (이 퍼널의 전환 포인트)
  → 경비 breakdown · 일자별 동선 열람
  → 연관: 그 여행에서 묵은 숙소 리뷰 / 방문한 여행지
  → 숙소 예약 제휴 링크 클릭 or 뉴스레터
```
**설계 함의**: 여행 리뷰는 **서로 연결될 때 가치가 커진다.**
"삿포로 3박4일" 안에 "그랑벨 호텔"과 "조잔케이"가 들어있는 구조.
→ `Review` 간 **부모-자식 관계**(`parentReviewId`)를 스키마에 둔다. 관련글 알고리즘으로 대체 불가.

### 4.3 댓글 작성 (인증 필요)
```
상세 하단 댓글 → 로그인 안 됨 → "카카오로 3초 로그인" 모달
  → OAuth → 원래 위치 복귀(리다이렉트 파라미터 유지) → 작성
  → 상태 PUBLISHED (기본) / 스팸 의심 시 PENDING → 어드민 검수
```

### 4.4 뉴스레터 구독 (더블 옵트인)
```
폼 제출 → 이메일 형식 검증(클라) → POST /subscribers (status=PENDING)
  → 확인 메일 발송 → 링크 클릭 → /newsletter/confirm?token=
  → status=CONFIRMED
```
> 「정보통신망법」상 영리 목적 광고성 정보 수신 동의가 필요하므로 **더블 옵트인 + 수신동의 체크박스 + 해지 링크**는 선택이 아니라 필수다.

| **비교** | **비교 대상 N개 등록, 항목별 비교표, "우리의 선택" 결론** |
| **테마** | **다크 모드 (토글 + localStorage + OS 연동 + FOUC 방지)** |
| 탐색 | 카테고리·상황태그 필터, 정렬, 검색(제목+결론+태그), 페이지네이션 |
| 미디어 | 이미지 업로드(오브젝트 스토리지), 리사이즈, blur placeholder, alt 필수 |
| 인증 | 관리자 이메일+비밀번호 / 일반회원 소셜(카카오·구글) |
| 댓글 | 작성·수정·삭제, 1단계 대댓글, 어드민 숨김/삭제, 신고 |
| 반응 | 리뷰 "도움이 됐어요" (로그인 시 1회) |
| 뉴스레터 | 더블 옵트인 구독, 해지, 어드민 발송(이슈 작성 + 발송) |
| 제휴 | 링크 관리, `/go/[id]` 리다이렉트 클릭 집계, 고지 배너 자동 노출 |
| 애널리틱스 | GA4, 자체 조회수, 제휴 클릭 대시보드 |
| SEO | 메타/OG, JSON-LD(Review·Article), sitemap, RSS, canonical |

> **범위는 늘었지만 일정은 줄었다.** rev.2로 In Scope가 4개 영역 늘었으나,
> 스택을 Payload로 바꾸면서 인증·미디어·어드민 UI·권한·드래프트 구현이 통째로 사라져
> **전체 8주 → 4주**가 되었다. ([로드맵](./03-tech-spec.md))
>
> 리뷰 타입 5종의 어드민 에디터 분기는 Payload의 `admin.condition`(필드 조건부 노출)으로
> 스키마 선언만으로 처리된다. 별도 화면 개발이 필요 없다.
>
> 그래도 일정이 빠듯하면 **`COMPARISON` 타입을 v1.1로 미루는 것**이 가장 효과적인 축소안이다.
> (카테고리 카드는 남기고, 비교 콘텐츠는 일반 리뷰로 우선 작성)

## 6. 콘텐츠 운영 정책 (기획 확정 사항)

| 항목 | 정책 |
|---|---|
| 발행 주기 | 주 1~2건 (실경험 기반이므로 무리하지 않음) |
| 최소 사용 기간 | `PRODUCT` 발행 전 **최소 1개월** 사용. 3/6/12개월 시점 재평가 |
| **여행 발행 기준** | **`TRIP`·`STAY`는 다녀온 뒤 2주 이내 작성** (기억이 흐려지기 전). 재평가 대상 아님 |
| 재평가 알림 | 어드민 대시보드에서 "재평가 대상" 자동 리스트업 (마지막 평가 후 90일 경과, `PRODUCT`만) |
| 협찬 표기 | `acquisitionType` 필수 입력. 미입력 시 발행 불가 (validation) |
| 단점 필수 | 단점(`cons`) **최소 1개** 없으면 발행 불가 — 서비스 정체성 강제 |
| **총경비 필수** | **`TRIP`은 총경비, `STAY`는 1박 요금 미입력 시 발행 불가** — 여행 섹션의 차별점 강제 |
| 댓글 정책 | 광고·욕설 자동 필터 + 신고 3회 시 자동 숨김 |
| 이미지 | 직접 촬영 원칙. 제조사 이미지 사용 시 출처 표기 |
| **개인정보** | **여행 사진의 GPS EXIF 제거 필수. 집 내부 사진에 주소·차량번호·타인 얼굴 노출 금지** |

> "단점 최소 1개 없으면 발행 불가", "총경비 없으면 발행 불가"는 코드 레벨 제약으로 구현한다.
> 기획이 코드로 강제되는 몇 안 되는 지점이며, 이 둘이 서비스의 약속을 지탱한다.
